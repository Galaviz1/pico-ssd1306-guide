Raspberry Pi Pico · I²C

Wiring an SSD1306
OLED to the Pico

Four jumper wires, one I²C bus. This walks the physical connections, then the software needed to put text on a 128×32 display — including two fixes specific to the board this was tested on.

  • Pico · RP2040
  • SSD1306 128×32
  • I²C @ 0x3C
  • MicroPython 1.29

The connections

OLED pinPico physical pinPico labelCarries
SDA pin 1 GP0 I²C data
SCL pin 2 GP1 I²C clock
GND pin 3 GND 0 V reference
VCC / VDD pin 36 3V3(OUT) 3.3 V power
Two things to get right

Power from pin 36, not pin 40. Pin 40 is VBUS — raw 5 V from USB. Many SSD1306 modules tolerate it on VCC, but the module's pull-up resistors then hold SDA and SCL at 5 V, which is outside the RP2040's input spec.

Read the silkscreen before you plug anything in. The four-pin header ships in several orders — GND VCC SCL SDA and VCC GND SDA SCL are both common. Match by the printed label, never by position.

Wiring it up

  1. Unplug the Pico

    Do the wiring with no USB cable attached. A slip between 3V3 and GND on a live board is the one mistake here that can damage something.

  2. Find pin 1

    Hold the Pico with the USB connector pointing away from you. Pin 1 is the top-left pad; pins 1, 2 and 3 run down that left edge. Pin 36 is on the right edge, fifth down from the USB end.

    Some Picos print pin numbers on the underside. If yours doesn't, count from the USB corner.

  3. Connect GND first

    OLED GND → Pico pin 3. Ground first is a habit worth keeping: it gives the two boards a shared 0 V reference before any signal or supply line is live.

  4. Connect power

    OLED VCC → Pico pin 36, the 3V3(OUT) pad. This is the longest jumper, since it crosses to the far edge of the board.

  5. Connect the bus

    OLED SDA → Pico pin 1 (GP0), and OLED SCL → Pico pin 2 (GP1). Swapping these two is the single most common wiring error, and it fails silently — the scan in step 7 simply finds nothing.

  6. Check before powering

    Look along the four wires once more against the table above. On a breadboard, tug each jumper gently — a wire resting in a hole rather than seated in it will pass a scan and then fail mid-transfer.

  7. Plug in and scan

    Connect USB and run the scan. A working display answers at 0x3C:

    from machine import Pin, SoftI2C
i2c = SoftI2C(sda=Pin(0), scl=Pin(1), freq=400_000)
print([hex(a) for a in i2c.scan()])   # -> ['0x3c']

    Nothing found means a wiring fault, not a software one. Jump to troubleshooting below.

Why SoftI2C

The RP2040 has two hardware I²C blocks, and GP0/GP1 are the standard pins for I2C0. On the board this guide was tested on, that hardware block does not work with this display: it finds the device during a scan, then NAKs every data byte that follows, identically from 400 kHz all the way down to 20 kHz. It also falsely acknowledges address 0x3D, where nothing is connected.

SoftI2C bit-bangs the same two pins in software and works perfectly — correct writes, correct reads, and an honest ENODEV for the empty address. For a display it costs nothing noticeable.

Getting code onto the board

The Pico needs MicroPython, plus a driver for the SSD1306. The driver is a single file, ssd1306.py, from MicroPython's own library — copy it to the board once and it stays there.

# install the tool that talks to the board
pip3 install --user mpremote

# copy the driver across (once)
mpremote connect /dev/cu.usbmodem141401 cp ssd1306.py :

# run a script from your computer on the board
mpremote connect /dev/cu.usbmodem141401 run oled_demo.py

Your port name will differ. On macOS it looks like /dev/cu.usbmodem…, on Linux /dev/ttyACM0, on Windows a COM number.

Blinking text

# oled_demo.py — text that blinks once a second
from machine import Pin, SoftI2C
from ssd1306 import SSD1306_I2C
import time

ON_MS = 1000
OFF_MS = 1000

i2c = SoftI2C(sda=Pin(0), scl=Pin(1), freq=400_000)
oled = SSD1306_I2C(128, 32, i2c, addr=0x3C)


def draw(visible):
    oled.fill(0)
    if visible:
        oled.text("Hello, Pico!", 0, 4)
        oled.text("SSD1306 128x32", 0, 18)
    oled.show()


try:
    while True:
        draw(True)
        time.sleep_ms(ON_MS)
        draw(False)
        time.sleep_ms(OFF_MS)
except KeyboardInterrupt:
    oled.fill(0)          # leave the panel blank on Ctrl-C
    oled.show()

The display is 128 px wide by 32 tall, and the built-in font is 8 px — so four lines of text at most, at y values like 0, 8, 16 and 24. The two rows above sit at 4 and 18 for a little breathing room.

Troubleshooting

SymptomMost likely causeWhat to do
Scan returns [] SDA and SCL swapped, or a wire not seated Swap the two data wires and scan again — it is the fastest test, and harmless
Scan finds 0x3C, then OSError: [Errno 5] EIO Hardware I²C block, or a marginal contact Switch I2C(0, …) to SoftI2C(…); if it persists, reseat every jumper
Display stays dark, scan fine Wrong geometry for the panel Try SSD1306_I2C(128, 64, …) — many modules sold as 128×32 are 64 tall
Image shifted sideways or doubled It is an SH1106, not an SSD1306 Use an SH1106 driver — it needs a 2-pixel column offset
Brief flash, then nothing Power on VBUS, or a brownout Move VCC to pin 36 and check the ground wire
No serial port appears at all No MicroPython, or a stuck BOOTSEL button Check rp2.bootsel_button() — a constant 1 means the button is stuck and the board enters the bootloader at every reset
Pin reference

The Pico exposes I2C0 and I2C1 on many pin pairs, so GP0/GP1 is a convention rather than a requirement. GP4/GP5, GP2/GP3 and GP26/GP27 all work — and with SoftI2C, any two free GPIOs do. GP0/GP1 simply sit next to a ground pin, which keeps the wiring short.

Tested on a Raspberry Pi Pico (RP2040) running MicroPython v1.29.0 with a 0.91″ SSD1306 128×32 module at address 0x3C.
